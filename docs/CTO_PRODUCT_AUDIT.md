# Menarium — CTO-аудит продукта и бизнес-логики

**Дата фиксации по коду:** апрель 2026  
**Метод:** только фактическое состояние репозитория (страницы App Router, API routes, Prisma, связанные UI). Новый функционал в рамках документа не специфицируется.

---

## A. Executive summary — главные продуктовые дыры

1. **Профиль объявлен как продуктовая зона, но часть маршрутов отсутствует в коде**: с главного профиля ведут ссылки на `/profile/edit` и `/profile/chats`, в `src/app/profile/` **нет** соответствующих `page.tsx` (только `page.tsx` и `my-swaps/page.tsx` с редиректом). Это **ломающий сценарий** (404), не «полировка».

2. **Цепочка «предложил обмен → понятный следующий шаг» обрывается в UI**: на `item/[id]` после успешного `POST /api/exchange` вызывается `setOpen(false)` — диалог закрывается, сообщение об успехе живёт **внутри** `DialogContent` (`src/app/item/[id]/page.tsx`, `handleExchange`). Пользователь **не получает устойчивого финала** (нет перехода на «Мои обмены», нет баннера на странице карточки).

3. **Завершение сделки и роли сторон асимметричны и не оформлены как продукт**: `PATCH /api/exchange` разрешает менять статус **только `receiverId`** (`src/app/api/exchange/route.ts`, проверка `swap.receiverId !== session.user.id`). Кнопка «Завершить» на **странице обменов** показывается **только** во вкладке «Входящие» для `ACCEPTED` (`src/app/exchange/page.tsx`). У **отправителя** заявки нет кнопки завершения — только «Чат обмена». Если получатель не нажмёт «Завершить», сделка **зависает в `ACCEPTED` / `IN_DEAL`**. Отмены сделки инициатором после принятия **нет**.

4. **Дублирование и «мёртвые» модели чатов**: в схеме есть `Chat` + `ChatMessage` и API `src/app/api/chat/route.ts`, но экран обменов использует **`Message`, привязанный к `SwapRequest`** через `src/app/api/exchange/[swapId]/messages/route.ts`. Модель `Chat` в пользовательских сценариях **не задействована**. Параллельно **отдельный** контур `ItemThread` / `ItemMessage` для чата по объявлению — без списка тредов для «Мои чаты».

5. **`ExchangeChain` в Prisma есть, в коде приложения не используется** (только миграция и `src/types/index.ts`). Любая «цепочка обменов» или расширенная модель сделки **не реализована**.

6. **Уведомления ведут на URL с параметром, который UI не обрабатывает**: при создании обмена и сообщениях в чате обмена в `href` кладётся `/exchange?swap=…` (`src/app/api/exchange/route.ts`, `src/app/api/exchange/[swapId]/messages/route.ts`). Страница `src/app/exchange/page.tsx` **не читает** `searchParams` — нет автофокуса на нужной заявке, открытия чата, смены вкладки.

7. **Оценка сделки, рейтинг, явный архив сделок в профиле**: в `schema.prisma` **нет** сущности отзыва/рейтинга; архив объявлений — это `Item.status = 'ARCHIVED'` при `COMPLETED` обмена. Отдельного «архива сделок» или истории с оценкой **нет**.

8. **Удаление объявления без учёта активной сделки**: `DELETE /api/items/[id]` не проверяет `IN_DEAL` / связанные `SwapRequest` (`src/app/api/items/[id]/route.ts`), в отличие от `PATCH` (редактирование блокируется для `IN_DEAL`). Риск **логического разрыва** данных.

## Идеальная цепочка обмена 1:1 vs реализация

**Целевая цепочка (как продукт):** просмотр чужого объявления → предложение обмена → уведомление получателя → принятие/отклонение → согласование в чате → **совместное или одностороннее подтверждение факта обмена** → **архив/история** → **остаточная ценность (оценка, репутация)** → отражение в профиле.

**Факт по коду:**

| Звено | Есть? | Где |
|-------|-------|-----|
| Просмотр, предложение | Да | `item/[id]`, `swipe`, `POST /api/exchange` |
| Уведомление получателю | Да | `notification` в POST |
| Принятие/отклонение получателем | Да | `PATCH`, `exchange/page.tsx` |
| Чат после принятия | Да | `Message` + модалка |
| Завершение и архив предметов | Частично | Только получатель жмёт «Завершить»; отправитель в зависимости от ожиданий в тупике |
| Оценка | Нет | Нет модели |
| История/архив сделок в профиле | Нет | Только общий список на `/exchange` |
| Deep link из уведомления | Нет | `?swap=` не используется |
| Отмена / эскалация | Нет | Нет |

## C. Приоритеты (что чинить первым)

1. **critical**: Завершение сделки и роли (политика: кто завершает, обоюдное подтверждение или SLA; иначе вечный `ACCEPTED`). Код: `src/app/api/exchange/route.ts`, `src/app/exchange/page.tsx`.
2. **critical**: Битые маршруты профиля (`/profile/edit`, `/profile/chats`) — либо страницы, либо убрать ссылки. Код: `src/app/profile/page.tsx`.
3. **high**: Финализация UX после отправки обмена с карточки. Код: `src/app/item/[id]/page.tsx`.
4. **high**: Обработка `?swap=` на `/exchange` (+ опционально открытие чата). Код: `src/app/exchange/page.tsx`, уведомления уже задают `href` в API.
5. **high**: `DELETE` объявления vs активные сделки. Код: `src/app/api/items/[id]/route.ts`.
6. **medium**: Единая стратегия чатов (`Chat` vs `Message` vs `ItemMessage`) или явное объявление legacy; список тредов для «Мои чаты».
7. **medium**: Отзыв исходящего `PENDING` отправителем — если нужен по продукту. Код: новая ветка в `PATCH` или отдельный маршрут.
8. **low**: Синхронизация `REJECTED`/`DECLINED` в типах и подписях; оценки — отдельный эпик после модели.
