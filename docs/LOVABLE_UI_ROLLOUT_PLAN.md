# План внедрения UI/UX из донора Lovable (Menarium)

**Статус:** актуальная стратегия + справочник по экранам (фазы A–K)  
**Основа:** анализ выгрузки Lovable (`menarium-source.txt`) и сопоставление с реальной кодовой базой Next.js Menarium  
**Цель документа:** зафиксировать порядок работ, границы scope и критерии приёмки.

---

## Стратегия внедрения (актуальная — ускоренная)

**Сдвиг:** не идём цепочкой «сначала только токены → потом UI → потом экраны». Приоритет — **быстрое ощущение нового продукта**, а не долгая подготовка UI-kit.

### Волна 1 (один крупный PR допустим и ожидаем)

В одном проходе внедряем:

- **Navbar** — реальные маршруты, уведомления только из API (без мок-ссылок донора).
- **Layout** — оболочка приложения (в т.ч. mobile bottom nav, если входит в дизайн).
- **Базовые стили** — цвета, типографика, радиусы, glass/glow в рамках `globals.css` / `tailwind.config.ts` по необходимости.
- **Карточки** — согласованный визуал списков и канон `ItemCard` (каталог как эталон композиции).

**Не застреваем** на отдельной длинной фазе «собрать весь UI-kit заранее». Нужный примитив — **по ходу** внедрения экрана.

### Волна 2 (сразу после волны 1)

- **Главная** (`src/app/page.tsx`) — вход в продукт (CTA: каталог, свайп, создать), а не «чистый маркетинговый лендинг» без связи с приложением.
- **Каталог** (`src/app/catalog/page.tsx`) — сетка, фильтры, empty/loading визуально по донору; **логика запросов и query — без изменений**.

**Цель волн 1–2:** уже на первом этапе виден **новый Menarium целиком** (навигация + ключевые экраны), а не точечные косметические правки.

### Принципы

1. **Крупный PR** на волнах 1–2 — нормальная практика, если покрыты smoke-тесты и ревью.
2. **Бизнес-логика, API, Prisma, NextAuth, жизненный цикл сделки, два контура чатов — не трогаем** без отдельного согласования.
3. **UI и UX-композиция** — переносим и улучшаем по донору в рамках редлайнов продукта (обмен, не магазин; без обещаний AI без бэкенда).

### Дальнейшие работы

Разделы **«Фазы A–K»** ниже остаются **справочником** по экранам, состояниям и критериям приёмки. Фактический порядок после волн 1–2 — по приоритету (профиль + inbox, exchange, item, create/edit и т.д.), без обязательной последовательности «сначала только foundation».

## 1. Цель и границы

### Цель

Перенести в продукт проверенные **визуальные и UX-решения** донора (композиция, навигация, плотность, состояния, motion-ритм), **не ломая** маршруты Next.js App Router, API, Prisma, NextAuth и текущую бизнес-логику.

### Не является целью

- Замена стека на Vite + React Router.
- Копирование мок-данных из донора.
- Внедрение «AI-создания объявления» и витрины цен в ₽ без продуктового решения и бэкенда.
- Превращение чатов в один полноэкранный мессенджер как **единственную** продуктовую модель (в Menarium два контура: обмен и объявление).

### Принцип

Донор = **референс слоя представления**. Источник истины по сценариям и сущностям — **текущий код Menarium**.

---

## 2. Предпосылки (до старта работ)

1. Зафиксировать **канон маршрутов** и не повторять ошибки донора: `/new` для создания (не `/create` как основной путь); основной раздел обменов — `/exchange`; inbox чатов — `/profile/chats`.
2. Подтвердить **канон визуала карточки объявления** (каталог, «Мои объявления», свайп — согласованная геометрия и иерархия, в рамках текущего `ItemCard`).
3. Зафиксировать **модель чатов и сделок** как в проде: два контура сообщений, жизненный цикл `SwapRequest`, read/unread — без «переезда» всего общения в один экран без отдельного эпика.
4. Определить ответственного за **design tokens**: расширение Menarium DS vs точечное выравнивание с донором **без** дублирования полного второго UI-kit (shadcn «как в доноре» целиком). *В ускоренной стратегии токены вводятся вместе с волной 1, а не отдельным месяцем.*

## 3. Фазы внедрения (справочник)

Ниже — детализация по зонам. **Волны 1–2** покрывают суть бывших фаз A (foundation + shell) и части B+C (главная + каталог) в ускоренном порядке.

### Фаза A — Фундамент (DS + навигация)

**Задачи**

- Свести глобальные паттерны донора к существующему DS: glass, градиенты, радиусы, типографика — через токены (Tailwind / CSS variables).
- Переработать shell / Navbar: desktop pill + при необходимости mobile bottom bar; все ссылки — на **реальные** маршруты (`/new`, `/exchange`, `/profile`, `/profile/chats`, `/catalog`, `/swipe`).
- Выровнять **уведомления**: визуал dropdown как у донора; **контент и `href`** только из API (не использовать мок-ссылки вида `/exchanges`, `/chats` из донора).
- Проверить доступность: focus, клавиатура, контраст активных пунктов.

**Критерии приёмки**

- Все CTA в шапке ведут на существующие маршруты.
- Нет регрессий auth-guard на защищённых разделах.
- Единый визуальный язык на 2–3 пилотных экранах без дублирования компонентов.

**Риски:** перегруз motion — уважать `prefers-reduced-motion`, не анимировать длинные списки агрессивно.

---

### Фаза B — Лендинг и статические страницы

**Задачи**

- `src/app/page.tsx`: hero, секции ценности, CTA — композиция по донору; тексты и ссылки на **реальные** разделы.
- `/privacy`, `/terms`: контейнер и типографика длинного текста в стиле DS.
- `not-found`: тон и CTA (например, в каталог) в согласованном стиле.

**Критерии приёмки**

- Лендинг не обещает AI и «магазинные» фичи без бэкенда.
- Нет битых ссылок.

---

### Фаза C — Каталог и списки

**Задачи**

- `src/app/catalog/page.tsx`: поиск, фильтры, чипы, сетка — **композиция** как у донора; **не менять** контракт query-параметров и логику фильтрации без отдельной задачи.
- Убрать визуальный акцент на «цену в ₽»; опора на поля обмена (что отдаю / что хочу, город, категории в терминах продукта).
- Единые паттерны empty / loading / error.

**Критерии приёмки**

- Фильтрация и загрузка данных работают как сейчас.
- Карточки соответствуют канону `ItemCard`.

---

### Фаза D — Карточка объявления и обмен

**Задачи**

- `src/app/item/[id]/page.tsx`: галерея, иерархия контента, блок обмена, модалки — визуально ближе к донору; **flow без изменений** (выбор своего объявления → `POST /api/exchange`, чат по объявлению).
- Сохранить ограничения по fullscreen-галерее и механике, зафиксированные ранее в UI-roadmap.

**Критерии приёмки**

- Статусы `ACTIVE` / `IN_DEAL` / `ARCHIVED` отображаются предсказуемо.
- Deep-link `?thread=` и возврат «Назад к чатам» не ломаются.

---

### Фаза E — Создание и редактирование

**Задачи**

- `src/app/new/page.tsx`, `ItemFormLayout` / формы редактирования: плотность полей, группировка, иерархия кнопок — по донору **без** AI-шага и **без** новых полей без изменения API.
- `src/app/item/[id]/edit/page.tsx`: то же визуальное выравнивание; явные состояния при запрете редактирования (`IN_DEAL`, `ARCHIVED`).

**Критерии приёмки**

- Upload, порядок изображений и валидация не регрессируют.

---

### Фаза F — Мои объявления

**Задачи**

- `src/app/my-items/page.tsx`: сетка, empty state, связь визуально с каталогом (фаза C).

**Критерии приёмки**

- Канон `ItemCard` соблюдён.

---

### Фаза G — Обмены (ядро продукта)

**Задачи**

- `src/app/exchange/page.tsx`: карточки сделок, вкладки, статусы, матрица подтверждений, кнопки — визуальная унификация с донорским экраном обменов **строго** под реальные действия: `accept`, `decline`, `complete`, `cancel`, `revoke` и реальные статусы.
- Модалка чата обмена: визуал ленты сообщений и поля ввода ближе к донору; сохранить read-only при `COMPLETED` / `CANCELLED`.

**Критерии приёмки**

- Сценарии двух пользователей (предложение → принятие → чат → завершение / отмена) проходят.
- Deep link `?swap=` работает.

---

### Фаза H — Профиль и inbox

**Задачи**

- `src/app/profile/page.tsx`: хаб, метрики, превью блоков — усилить визуально по донору; данные только из БД/API.
- `src/app/profile/chats/page.tsx`: опционально — split-pane (список + контекст) как в донорском `ChatsPage`; **переходы** сохраняют текущий контракт: swap → `/exchange?swap=…`, item → `/item/…` с `thread` при необходимости.

**Критерии приёмки**

- Unified inbox, непрочитанные и разделение типов чатов не регрессируют.
- Нет кнопок без реального действия.

---

### Фаза I — Свайп

**Задачи**

- `src/app/swipe/page.tsx` + компоненты стека: визуальное выравнивание с донором; **без** новой логики жестов без согласования.

**Критерии приёмки**

- `skip` / `wantExchange` и фильтры работают как сейчас.

---

### Фаза J — Auth

**Задачи**

- `src/app/auth/login`, `src/app/auth/register`: визуал форм и сообщений об ошибках — по донору; NextAuth и редиректы **без изменений**.

**Критерии приёмки**

- Нет регрессий (в т.ч. поведение query-параметров вроде `registered=true`).

---

### Фаза K — Полировка и регрессия

**Задачи**

- Пройти полный чек-лист маршрутов из матрицы ниже.
- Единые empty / error / loading по продукту.
- Мобильная нижняя навигация (если внедрена): safe area, перекрытие контента.
- Короткий внутренний документ: «что перенесли из донора / что отвергли и почему».

**Критерии приёмки**

- Подпись CTO на чек-листе ключевых сценариев.

## 5. Риски и митигация

| Риск | Митигация |
|------|-----------|
| Дублирование DS и полного shadcn-kit из донора | Расширять Menarium primitives и токены точечно |
| «Магазинный» UX (цена как главный атрибут) | Редлайн: не делать ₽ центральным сигналом карточки |
| Конфликт одного мессенджера vs два API чатов | Улучшать inbox композицией; не менять модель без эпика |
| Производительность из-за motion | Ограничить анимации списков; `prefers-reduced-motion` |
| Регресс маршрутов | Чек-лист ссылок после волн 1–2 и при крупных изменениях shell |

---

## 6. Критерии успеха проекта (для CTO)

1. Все значимые маршруты визуально согласованы с утверждённым направлением донора **без** изменения бизнес-логики и контрактов API.
2. Нет новых пользовательских обещаний (AI, витрина цен, обязательный `/chats`), если нет бэкенда и продуктового решения.
3. Ключевые сценарии обмена и чатов проходят ручной регресс (два аккаунта).
4. Навигация и уведомления ведут только на корректные URL продукта.
5. Зафиксирован короткий **design-to-code mapping** (что взято/отвергнуто) для следующих итераций.

## 8. Порядок старта

Крупный PR на волнах 1–2 — допустим; параллелить foundation и «только токены» отдельно от экранов **не требуется**.
